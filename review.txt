Performance Evaluation of the MCTS
Implementation
Current Throughput vs. Targets
The Monte Carlo Tree Search (MCTS) engine in this repository is significantly underperforming relative to
its hardware-grounded targets. On the given AMD Ryzen 9 5900X (12C/24T) + RTX 3060 Ti setup, the current
throughput is only ~2,147 simulations/sec, which is a regression from the earlier ~3,831 sims/sec baseline
   1 . The project’s revised realistic goal is ≥8,000 sims/sec (stretch to ~10k) on this hardware 2   3 . In

other words, the MCTS is currently achieving barely ~26% of the 8k target. Below, we critically analyze why
it’s so slow, then propose concrete improvements to recover and surpass the baseline throughput.


Bottleneck Analysis of MCTS Performance
1. Disproportionate MCTS Overhead vs GPU Work: Profiling shows only ~32.8% of time spent in neural
network inference on GPU, while a massive 67.2% is consumed by MCTS coordination (selection, expansion,
backup, thread sync) 4 . In other words, the CPU-side MCTS logic is the dominant bottleneck, not the
GPU. This is despite keeping the neural net in Python (PyTorch) – which is acceptable since GPU inference
isn’t the limiting factor 5 . The implication is that to reach 8k+ sims/sec, we must drastically reduce the CPU
overhead per simulation.


2. Feature Extraction Not Parallelized (Critical Blocker): The conversion of game states to NN input
features is a major slowdown. Currently, the create_batch_tensor_from_states() in C++ runs
mostly single-threaded (OpenMP not effective), costing ~7.5ms per batch of 64 states 6 . This adds ~7–
8ms latency to every inference batch, capping overall throughput around ~1.6k–2.1k sims/sec 1 . In fact,
the repo explicitly flags that missing OpenMP parallelization in the feature extraction loop is a critical
performance bug, causing the observed regression 1 . Until this is fixed, the MCTS cannot fully utilize the
GPU.


       Evidence: The current 2,147 sims/sec was measured with the feature-extraction loop non-
       parallelized (OpenMP off) 1 . Parallelizing this should cut batch preparation to <1ms,
       eliminating ~7.5ms of overhead each batch and immediately restoring a large chunk of
       throughput.


3. Excessive State Cloning and Python Coordination Overhead: The design currently clones the game
state 2–3 times per simulation, which is extremely wasteful 7 . For each simulation thread:
- It clones the root IGameState at the start of run_simulation() 8 .
- In continuous mode, it again clones the state for queue submission (see                 queue_state      =
current_state->clone() in continuous runner)          9   .
- The AsyncInferenceQueue.submit_request() then internally clones yet again when enqueuing (it
calls state->clone() in a loop) 10 .




                                                      1
These redundant copies inflate per-simulation CPU time. The spec explicitly lists “state cloning waste (2–3×
per simulation)” as a key issue 6 . Moreover, each clone likely allocates and copies the entire board state
(e.g. 225-cell Gomoku board with feature planes), which adds up in a multi-threaded setting. This not only
wastes CPU cycles but also increases pressure on Python’s garbage collector (if Python objects are involved)
and memory bandwidth. In summary, the current coordinator/orchestration is far from zero-copy in
practice, despite using DLPack for tensor data.


Additionally, although the new async batching design drastically cut down Python GIL acquisitions (to one
per batch), there is still some Python-layer overhead in building batch lists and converting results. The
engine’s analysis found Python/GIL overhead still accounts for ~67% of total runtime 6 . This includes
things like: preparing Python lists of state pointers for PyBatchInferenceCallback , calling
torch.from_dlpack , and packaging results back to C++. There is room to streamline these crossings
further.


4. Inefficient Multi-Thread Scaling and Idle Time: The MCTS shows poor parallel scaling beyond 2–4
threads. In earlier tests, throughput peaked at ~3,831 sims/sec with 4 threads, then dropped to ~3,355 at 8
threads 11 – a mere ~12.5% efficiency gain from doubling threads 7 . At 12 threads it plunged to ~3,062
(~16% efficiency) 12 . Several factors explain this:


      • Thread Contention & Locking: Even though much of the tree is lock-free/atomic, some global locks
        remain. Notably, node allocation uses a global mutex when expanding multiple children (see
         allocate_nodes() using allocation_mutex_ ) 13 14 . When many threads expand new
       nodes concurrently (especially early in search when many leaves are unexpanded), they serialize on
       this lock. This can cause threads to stall. The severity increases with thread count – more threads
       trying to expand leads to more waiting. Although a thread-local node pool (4096-block per thread)
       exists for single-node allocations 15 16 , the contiguous allocation of children still takes the slow
       path lock for each expansion. With, say, 8 or 12 threads all rapidly expanding leaves, this becomes a
       bottleneck. The result is threads often sit idle ~60% of the time 6 instead of doing useful work.


      • Atomic Updates & False Sharing: The shared tree design means certain hot fields (e.g. root’s visit
        count and value) are updated atomically by all threads. The backup phase thus incurs contention –
        e.g. every simulation does an atomic add to the root node’s visit count. The code attempts to
        mitigate this by batching updates (Phase 3/4 in process_completed_results() accumulates
       increments per node) to cut atomic ops roughly in half 17 . Still, heavy contention on a few cache
       lines (root and high-level nodes) with many threads can reduce scaling. (That said, collision
       mitigation like virtual loss and busy-edge masking do prevent most simultaneous expansions of the
       same node, keeping contention at acceptable levels – measured <0.5% collision rate at 4 threads
         18 .)




      • Thread Coordination & Waiting: In continuous search mode, threads run in a loop of Select →
       Queue → (possibly wait) → Process results. If a thread finds the leaf it wanted to expand is already
       being expanded by another thread, it must back off ( waiting_for_leaf = true ) 19 . The code
       then has that thread sleep briefly (e.g. 50–100µs) to avoid busy-waiting 20 21 . With more threads,
       such scenarios happen more often (especially at the start or in shallow trees), meaning threads
       spend more time sleeping. Likewise, if the inference queue is saturated (4096 in-flight cap) 22 or if a
       thread has submitted all its simulations and is just waiting for results, it will also sleep. All these
       coordination pauses add up: the review notes ~1.489s of a 2.5s search was thread idle time (~60%)




                                                      2
        6 . Essentially, beyond a certain number of threads, the extra threads mostly contend or wait,

       providing diminishing returns.


     • CPU Core Utilization: The optimal observed config was 2–4 threads on the 5900X; beyond that,
       efficiency plummeted 23 . This suggests either (a) the workload cannot effectively utilize more cores
       due to the synchronization overhead above, or (b) per-thread CPU saturation occurs (e.g. if each
       thread was already bottlenecked by the single inference thread). Given the GPU wasn’t fully utilized
       at 4 threads (only ~33% busy 4 ), the culprit is the former – i.e. internal contention. The thread
       affinity code pinning threads to distinct CCDs/cores is already in place 24 , which is good. But if 12
       threads share 6 physical cores (if using 24 hyperthreads), context-switching can further hurt
       performance. The code’s ThreadAffinityManager tries to pin by thread_id%24 which might actually
       spread threads suboptimally across SMT threads; binding strictly one thread per physical core might
       yield better results.


5. Busy-Wait on Results Batching: The use of a background BatchInferenceCoordinator is a huge
improvement (reduces GIL holds to one per batch). However, simulation threads currently still poll for
results in a tight loop with short sleeps. Specifically, ContinuousSimulationRunner calls
process_completed_results() each iteration; if it returns 0 (no new results ready), threads sleep 50–
100 µs and try again 21 . This is essentially a spin-wait on the inference results, which wastes CPU cycles.
A more efficient design would have threads block on a condition variable or semaphore that the
coordinator signals when a batch of results is ready. Right now, the coordinator does push results to the
queue but doesn’t explicitly wake simulation threads – they just periodically check. This contributes to the
high coordination overhead (threads doing useless loops). The code has already replaced active polling in
the coordinator itself with a condition variable (for waiting on requests) 25 ; extending a similar mechanism
to the simulation threads waiting on results could further cut overhead.


In summary, the primary reasons for slowness are: un-parallelized state feature extraction, excessive state
copying, suboptimal thread synchronization (with lock contention and spin-waiting), and residual Python
overhead in the batch interface. All these issues compound to yield only ~2k sims/sec instead of the 8k+ that
the hardware could theoretically handle 3 . Next, we detail how to fix these problems.


Recommendations for Throughput Improvement
To meet the ≥8,000 sims/sec target, significant optimizations and some design tweaks are needed.
Below is a comprehensive improvement plan:


     • A. Fix OpenMP Parallelization for Feature Extraction (Highest Priority): Enable and verify the
       OpenMP loop in dlpack_bridge.cpp so that feature extraction across a batch is multicore. This is
       a straightforward bug fix that should immediately roughly double current throughput. The goal
       is to bring the batch feature preprocessing down from 7.5ms to <1ms, as planned 26 . With this
       fix, the inference GPU can be fed at its full speed. In profiling terms, this should eliminate the ~7ms
       overhead per batch and remove the ~1,675 sims/sec cap due to CPU preprocessing 1 . Concretely:
       ensure the code is compiled with OpenMP support ( -fopenmp is in CMake, so check that the
       extension is loading the OpenMP-enabled binary). After the fix, re-profile – you should see GPU
       utilization jump and total throughput approach the prior baseline (~3.8k sims/sec) or higher. This
       addresses the critical blocker 1 .




                                                      3
     • B. Eliminate Redundant State Cloning: Re-architect the simulation coordination to avoid cloning
       game state multiple times per simulation. Several approaches can be combined:


     • Reuse state objects: Implement a pool of IGameState objects or a resettable state class for
       threads. For example, each thread can maintain a single current_state buffer that it reinitializes
       from the root state at the start of each simulation (by applying moves or copying board arrays)
       instead of calling full clone() constructors each time. The Constitution explicitly targets thread-
       local state reuse to avoid the “2–3× cloning per simulation” overhead 27 . This might require adding
       a method like IGameState.copy_from(other) to quickly copy core state data without heap
       allocations. By reusing pre-allocated state memory, you’ll cut simulation overhead and reduce GC
       pressure.
     • Pass State by Reference to Inference Queue: Refactor
        AsyncInferenceQueue.submit_request() to not clone the state internally. Currently it does
       request.state = state->clone() for each enqueue 10 . If we ensure that the state passed in
       will remain valid until inference completes, we can avoid this. One idea is to transfer ownership of
       the simulation thread’s current_state to the queue (std::move the unique_ptr without
       cloning). The thread would then not retain a copy – instead, after submitting, it would immediately
       allocate a fresh state for the next simulation. Meanwhile, the queue/coord holds the one for
       expansion. This way, each simulation only uses one state instance total (moved from thread to
       queue to pending result). It will require careful handling: the PendingExpansion already stores
       the state unique_ptr for use when the NN result returns 28 . We can leverage that: let the queue’s
       request hold a raw pointer or an index to the pending_buffer_ instead of a full clone. Essentially,
       unify the state object between PendingExpansion and InferenceRequest . This change would
       be a “surgical big fix” to cut out one whole clone operation per simulation.
     • Precompute Legal Moves and Current Player: In many cases, the only reason the state is needed
       after inference is to get legal moves and the current player for expansion. Notice that before
       queuing a request, we have just selected a leaf; we could call state.getLegalMoves() at that
       point (before losing the state) and stash that list in the InferenceRequest or
       PendingExpansion . If we record legal_moves and current_player in the request, then
       when the result comes back we can expand the node without needing to call state again. This
       means we wouldn’t strictly need the actual state object for expansion – the children’s moves and
       parent player are known. We could then free or recycle the state earlier. In practice, implementing
       this requires augmenting the InferenceRequest structure with a legal move list (which for
       Gomoku or small boards is fine). Then expand_node_with_result() can use the stored moves
       instead of calling state.getLegalMoves()          29 . This optimization complements state pooling by

       reducing the work each state must do.

By reducing clones, we attack both the CPU time per simulation and memory usage. The spec’s memory
management plan (node pools, epoch-based reset, etc.) already is quite efficient (27 bytes/node) 30 – but
the transient memory from repeated state clones is not yet optimized. Implementing the above should
greatly shrink Python coordination overhead (fewer object creations) and is likely to yield a major speedup,
as indicated by the design goal of 99.93% fast-path allocations via thread-local arenas 30 .


     • C. Improve Thread Coordination & Parallel Efficiency: To scale to 8+ threads at high efficiency, we
       must reduce contention and idle time:
     • Make Simulation Threads Truly Wait for Results: Replace the spin-loop + sleep in
        ContinuousSimulationRunner with a proper blocking mechanism. For example, use a condition




                                                     4
      variable that threads wait on when pending_count_ is zero (i.e. no results to process) and all
      simulations have been submitted. The BatchInferenceCoordinator can notify this CV when it
       submits a batch of results. This way, threads will sleep efficiently until there is work, rather than
       waking up every 50µs to check. Removing these micro-sleeps should cut CPU waste and free up
       cycles to do useful simulations. It will also lower the 60% idle statistic significantly. Essentially, push-
       based notification from the coordinator to workers, instead of polling.
     • Reduce Lock Contention in Node Expansion: The global allocation_mutex_ is a bottleneck for
      multi-node allocation 13 . Consider ways to mitigate this: one idea is to batch allocate children
      outside the lock by over-reserving nodes. For instance, if each thread’s local arena handed out
      indices in blocks (already done for single nodes), extend that idea for children: a thread could
      request a block of e.g. 256 nodes from the global pool at once and then carve it up for a few
      expansions without re-locking each time. Another approach is lock-free allocation for contiguous
      ranges – more complex, but perhaps unnecessary if the above state reuse reduces how often
      expansions happen simultaneously. At minimum, using a smaller critical section (e.g. computing
       first_index and updating indices with one atomic instead of a lock) might be possible. Keep in
       mind that after the tree grows large, expansions per second slow down (since many simulations hit
       already-expanded nodes), so this mainly affects the beginning of search or shallow games. Still,
       removing any frequent global lock will improve scaling.
     • Optimize Virtual Loss & Flags Updates: The virtual loss system (WU-UCT) is implemented with
       atomic flag toggling for the “expanding” bit 31 . The design is sound (visit-only loss, no Q distortion)
       and collisions are rare 18 . So we wouldn’t remove it, but ensure it’s efficient: use relaxed memory
       order where possible for non-contentious atomic ops, and avoid unnecessary cache misses (the code
       already aligns NodeFlags to 64 bytes and packs bits in a byte). One small improvement: the
        atomic_try_mark_expanding() loop uses compare_exchange_weak in a loop 32 – given
       how seldom it fails, that’s fine. No major changes needed here beyond what’s done.
     • Thread/CPU Affinity Tuning: Verify that the thread affinity is actually helping. The code pins threads
       based on a hash of std::thread::id % 24 33 . This is a bit of a hack; it might not evenly
      distribute threads on the 12 physical cores. You might want to pin the first 12 threads to cores 0–11
      explicitly (one per core) and avoid using SMT siblings until we saturate physical cores. This could
      yield a minor boost by reducing cross-CCX traffic (the code cited an expected 1.15× speedup from
      proper pinning) 24 . In short, ensure all 8 (or 12) threads you use are on separate physical cores to
      maximize parallel efficiency.

With these coordination improvements, we aim to achieve ~70–80% efficiency at 8 threads, per the project
goals 34 . That means 8 threads should run ~5–6× the speed of 1 thread, instead of the ~2.2× we saw. Given
the hardware, using 8 threads may be optimal; using all 12 might give a slight bump or could be
counterproductive if GPU becomes the bottleneck by then. We’ll revisit that in throughput estimates.


     • D. Streamline Python ↔ C++ Batch Interface: Although the batch inference pipeline is mostly
       optimized, we can trim remaining Python-side costs:
     • Leverage DLPack Bridge Fully: Ensure that when using the DLPackInferenceBridge (the fast
      path for batch inference), we’re not inadvertently converting data twice. The fast batch callback in
      Python already checks for isinstance(..., DLPackInferenceBridge) and calls
       inference_fn.batch_inference(game_states) directly 35 . This should use the C++
       create_batch_tensor_from_states under the hood with zero-copy to Torch. We need to verify
      this code path is active. If the user’s inference_fn was a GPUInferenceWorker wrapped in
       CppInferenceBridge , note that the fast callback currently treats it as non-dlpack and does an

 extra NumPy conversion for each state 36 . To avoid this, consider making CppInferenceBridge
 itself expose a batch_inference that accepts list of IGameState (not just numpy arrays).
 Alternatively, directly use DLPackInferenceBridge as the inference function. The goal is to avoid
 any per-state Python processing in the batch callback – ideally, one call into C++ creates a tensor
 for all states, and one PyTorch forward produces results. By ensuring all state feature extraction is
 done in C++ (with OpenMP) and results come back as NumPy arrays (which pybind11 can convert to
 std::vector<float> without Python loops), we minimize GIL time. The spec even mentions returning
 numpy arrays directly to eliminate Python list conversion overhead (~1–2ms saved per batch) 37
  38 .



• Reduce Result Handling Overhead: The PyBind PyBatchInferenceCallback currently converts
 the Python list of (policy, value) tuples back to C++ vectors element by element 39 40 . This is
 necessary given the design. But if we follow the above step (return NumPy arrays for policies), those
 will be converted to std::vector<float> by pybind11 more efficiently than Python lists. We
 should also ensure the batch size is large enough (e.g. 64) that this conversion cost is amortized.
 With batch=64, the overhead is small relative to GPU time – but every millisecond counts at 10k sims/
 sec scale. Another micro-optimization: avoid copying the policy vector twice. Currently, the C++
 callback does results.emplace_back(policy, value) which copies the vector; we could move
 it since we know the Python side created a new list or array for it. These are minor tweaks –
 individually small, but together they help reach the last mile of performance.


• No Libtorch Needed (Keep PyTorch in Python): Importantly, none of these changes require moving
  the neural network to C++ (libtorch). The Constitution explicitly prohibits libtorch/TensorRT to retain
 flexibility 41 5 . Given that GPU inference was only ~33% of time at 3.8k sims/sec 4 , doubling
 the raw neural net speed (which the user plans by simplifying the model) will directly raise
 throughput. We’ll harness that, but we can stick with the Python PyTorch interface. The batch
 dispatch approach means the GIL is only held briefly per batch, which is fine. The analysis indicates
 GPU can handle ~8k–10k states/sec at FP16 on this card 2 3 , so as long as our CPU-side
 generates ~8k+ states/sec, PyTorch (in Python) will not be the limiter. In short, libtorch/CUDA C++ is
 not mandatory – we can hit the target with the Python-based pipeline 5 . If we found CPU was still
 the bottleneck after all optimizations (unlikely if we follow through), only then would we consider
 offloading more to C++.


• E. Exploit Hardware Concurrency (CPU & GPU) Effectively: With all the above fixes, we should re-
  measure and tune:


• Thread Count: Aim to use enough CPU threads to keep the GPU busy without excessive
  contention. Based on the targets, this might be ~8 threads. If after optimizations 8 threads achieve
  ~8k sims/sec with ~80% GPU utilization, adding more threads won’t help (GPU-bound). If GPU
  utilization is lower, you can try 10–12 threads to push batch size higher (maybe average batch 64
  instead of 48). The framework can support 12 or more, but efficiency per thread may drop. The
  target criteria expects ~60–75% efficiency at 8 threads 34 – achieving that is a success. You likely
  won’t get linear scaling to 24 threads on this design due to fundamental shared tree overhead, so
  focus on optimal, not maximal, thread count.
• Batch Size & Timeout Tuning: The current default (batch_size=32, timeout=2ms) is reasonable 42 .
  After speeding up CPU tasks, you might find the coordinator often collects >32 states very quickly
  (especially with many threads). It could make sense to test batch_size=64 with a slightly longer or

       increase per-batch latency. Since our goal is throughput over raw per-sim latency (within bounds),

     • Profile and Verify Utilization: After all changes, instrument the run: we want CPU utilization high

Estimated Throughput After Improvements: Based on analysis and the project’s own estimates, the
hardware realistic throughput is about 8k simulations per second sustained 2 . With the heavy ResNet
replaced by a faster model (user’s plan), the GPU inference speed might roughly double, meaning even 10k
sims/sec could be attainable as a stretch goal 47 45 . The repository authors revised the target from 25k to
8–10k after factoring in the RTX 3060 Ti limits 48 2 . So we should aim for ~8k and consider 10k as the
optimistic upper bound 47 . Reaching 5k+ sims/sec is almost certain after implementing the above fixes
(even the OpenMP fix alone might bring it near that). Hitting ~8k will require all of the improvements
(especially state reuse and efficient scaling).


Finally, note that further architectural changes (e.g. root-parallel search, multi-GPU, transposition
tables) were explicitly ruled out of scope 49 50 . The plan above respects those constraints and focuses on
enhancing the existing shared-tree, CPU-parallel design 50 . It is “surgical” where possible (fixing bugs,
removing overhead) and maintains the Python interface for NN. By being blunt about the current
shortcomings and addressing them methodically, we can confidently expect to elevate the MCTS engine to
superhuman-strength throughput (8k+ sims/sec) on the given hardware, without resorting to forbidden
techniques. All recommendations align with the project’s own goals and will bring the implementation in
line with modern AlphaZero MCTS best practices: maximum hardware utilization, minimal coordination
overhead, and balanced CPU-GPU throughput 44 4 .

# 1) Transposition tables (TT): can they speed up MCTS without hurting play?

## Short answer

Yes—**if you scope them correctly.** The safest, high-ROI design is an **NN-evaluation cache** keyed by the state hash that *skips redundant network calls* but **does not** aggregate MCTS statistics across parents. That gives you real speedups with essentially zero risk to search stability. A more aggressive “full DAG” TT (merging statistics across all parents) can be even faster in transposition-heavy games, **but** requires careful graph backprop to avoid bias/instability.

## What to use in your setup (ranked)

**Tier A — Safe & easy (recommended now):**
**NN-eval cache (a.k.a. “policy/value cache”).**

* **What it does:** On expansion, check a hash-indexed cache; if there’s a hit, reuse `(π, V)` and **skip the GPU**. Still create a normal tree node per (parent, move).
* **Why it’s safe:** You don’t share N/W across different parents, so PUCT math and backups remain unchanged. You only avoid repeated inference. This is also the approach suggested in batch-MCTS literature (“TT stores inferences; the tree stores statistics”). ([arXiv][1])
* **Why it’s fast:** In chess (heavy transpositions) LCZero measured ~**50% tree reduction** when merging positions; even as a pure eval cache you’ll cut a large fraction of evals on typical positions. Key point: **don’t include full move history** in the key unless the rules demand it—history keys kill the benefit. In chess they found including Rule-50 counter is fine; in many games, history isn’t needed for Markov state. ([Leela Chess Zero][2])

**Tier B — Powerful but trickier:**
**Full DAG TT (merge statistics across parents).**

* **What it does:** One node per unique state; *all* parents share its stats (N, W, Q, P).
* **Upside:** Eliminates redundancy; exploration information propagates through the graph. Multiple papers/theses (“MCGS”) show how to do **stable DAG backprop** in AlphaZero settings. ([aiml.informatik.tu-darmstadt.de][3])
* **Risk:** If you naively sum visits/values and back them up through all parents, you can **bias UCB/PUCT** and destabilize selection (overcounting, loops, “reverberation”). Use a DAG-safe backup (no double-credit for the same traversal; edge-local stats; careful accumulation semantics) as in Monte-Carlo Graph Search. ([aiml.informatik.tu-darmstadt.de][3])
* **My recommendation:** Treat this as a **phase-2** optimization after Tier-A is solid and profiled.

## Implementation blueprint (for your codebase)

**Hashing (Zobrist):**

* Key = (board pattern, side-to-move, rule-flags).

  * **Chess:** include side-to-move, castling, en-passant, **Rule-50**; do *not* include full repetition history if you use NN-cache. ([Leela Chess Zero][2])
  * **Gomoku:** board + side-to-move (+ variant flag if Renju/Omok).
  * **Go 9×9:** board + side-to-move + ko point/superko flag depending on ruleset.
* Make a **64-bit Zobrist** with per-cell, per-color randoms; preseed by variant.

**Entry layout (NN-eval cache):**

* Minimal fields:

  * `uint64 hash; uint32 net_version;`
  * `uint16 n_moves;`
  * `float16/uint8[k] policy_topk` + `uint16[k] move_idx` *(or)* `float16[board_size] policy_full`
  * `float16 value;`
* Use **quantization** to cap memory: FP16 or int8 for policy; **top-K** (e.g., K=16..48) is typically enough for Gomoku/9×9 and greatly shrinks footprint.
* **Eviction:** per-net LRU or SLRU; **tag by net_version** so you can invalidate between training updates.

**Concurrency:**

* **Sharded hash table** (e.g., 64 shards), each with a small spinlock or reader-writer lock; or an open-addressed lock-free map (folly F14/abseil).
* **Fast path is look-up only** on expansion; on miss, proceed to normal enqueue; on fill, write back the eval. Lookups dominate; keep them wait-free or minimally locked.

**Integration point:**

* In your **leaf expansion path** (just *before* enqueuing a NN request), probe TT.

  * **Hit:** fabricate a “completed inference” result and push it straight into your result queue (skips GPU entirely).
  * **Miss:** enqueue as usual; when results return, **store** into TT.
* This drops right into your existing **centralized batching** (no libtorch needed).

**Expected gains on your hardware:**

* **Chess:** large (many transpositions) → frequent NN cache hits → 20–50% fewer GPU calls is realistic. ([Leela Chess Zero][2])
* **Gomoku/9×9 Go:** moderate but still meaningful; many non-interfering local moves commute into the same state → you’ll see sustained cache hit-rates during midgame.
* Because your measured bottleneck is largely on CPU-side MCTS, the win shows up as: (a) **bigger average batch sizes** (fewer tiny “drip” requests), (b) **higher GPU utilization** for the requests that remain, and (c) fewer Python crossings overall. (Batch-MCTS papers and Q&A describe exactly this split: TT holds inferences; tree holds stats.) ([arXiv][1])

# 2) Multiple MCTS in parallel for faster self-play: good idea or throughput killer?

## Short answer

It **usually helps throughput** on a single machine with **one GPU**—**if** you centralize inference batching. Running **many single-thread MCTS games in parallel** (each doing select/backup locally) and feeding a **single global inference queue** is now a standard pattern for AlphaZero/MuZero actors because it keeps the GPU busy with large, steady batches. ([Artificial Intelligence Stack Exchange][4])

## Why it helps (and when it doesn’t)

* **Helps when:** one MCTS instance can’t consistently fill large GPU batches within your short timeout (e.g., 1–2 ms). Multiple games “crowdsource” leaves so the coordinator almost always flushes **big batches** (e.g., 64), maximizing GPU throughput and hiding per-batch latency. This is exactly the actor→policy-worker pattern in modern RL. ([arXiv][5])
* **Can hurt when:** the CPU becomes saturated coordinating too many trees (context switches, cache thrash), or your per-game search becomes too shallow because they are competing for the same GPU. If you care about *move strength* during evaluation, you may want fewer concurrent games; but for **training data throughput**, more actors is typically better (to a point). Open implementations and discussions explicitly propose **running many MCTS threads/games that pause at leaf and batch NN calls**. ([Artificial Intelligence Stack Exchange][4])

## What to deploy on your 5900X/3060 Ti (practical plan)

* **Centralize NN inference** (you already have a batching coordinator).
* **Run many single-threaded MCTS games** (actors), not a few multi-threaded shared-tree searches. This sidesteps tree-level lock contention and the “threads idling 60%” problem.
* **Good starting point:**

  * **Actors:** 10–14 processes/threads (≈ one per physical core, plus 1–2 for the coordinator).
  * **Each actor:** single thread MCTS (leaf-parallel inside the actor is optional), queue leafs to the **one** global inference server.
  * **Coordinator:** batch size target 64, timeout 1–2 ms (tune).
* **Auto-tune** the number of actors to meet these telemetry targets:

  * Average batch size **≥ 0.8 × max_batch** (so ~51+ when max is 64).
  * GPU util **80–95%** during self-play.
  * Actor CPU util near **one core each**; coordinator low single-digit %.
* **When to switch:** If you see GPU under-utilized with one MCTS even after your feature-extraction fix, **add actors**. If GPU is pegged but actors idle waiting on results, **reduce actors or batch size**.

> This “many single-thread actors → one inference server” is exactly the pattern used in modern AlphaZero/MuZero codebases and RL frameworks to scale self-play efficiently on limited GPUs. ([arXiv][5])

# Caveats & best practices (both topics)

* **Training correctness:**

  * **NN-eval cache** is safe within a run. Across training updates, **flush by `net_version`** so you don’t reuse stale priors/values. ([arXiv][1])
  * **Full DAG TT** is fine in perfect-information games if you implement **graph-aware backup** (see MCGS); don’t just reuse tree backup on a merged graph. ([aiml.informatik.tu-darmstadt.de][3])
* **Keys & rules:** Don’t include extraneous history in the hash key; include only rule-critical counters (e.g., Chess Rule-50, Go ko). Including unnecessary history **destroys TT hit-rate**. ([Leela Chess Zero][2])
* **Memory limits:** NN-cache can grow huge. Use quantization + top-K and shard-LRU to cap to a budget (e.g., 2–8 GB depending on game).
* **Symmetries:** Optional: cache under a **canonical symmetry** (e.g., lexicographically minimal rotation/reflection) to boost hits, but only if you can apply the inverse transform cheaply to the policy vector at lookup time. The CPU cost sometimes outweighs the gain; measure before committing.
* **Profiling:** Add per-actor stats: queueing delay, average batch size, hit-rate of NN-cache, CPU time in select/expand/backup.

## Why multi-game concurrency usually helps

1. **Batching efficiency:** GPUs are happiest with bigger, steadier batches; multiple games “crowdsource” leaves so your batcher almost always flushes **near-max batch size**. This is a known best practice for AZ/MuZero self-play. ([Artificial Intelligence Stack Exchange][1])

3. **Throughput scaling:** Empirically, engines see strong **n/s** gains when batch size grows (classical Leela-Zero reports big jumps from 1 → 8 → 16+). You get those big batches *much* easier with multiple games. ([GitHub][2])

## Concrete design for your repo

### A) Architecture (actors + one inference server)

* **Actors = games**: Run **G** concurrent self-play games (processes or threads). Each actor runs its own (small-thread) MCTS loop.
* **One global batcher** (you already have one): All actors push leaf states to this **single** queue; the batcher builds **big batches (64)** and does a single PyTorch forward. This is standard in MuZero/AZ systems. ([repository.kulib.kyoto-u.ac.jp][5])
* **Result return**: The batcher demuxes results back to the right actor (game_id, request_id).

**Why this matches the literature:** It’s the accepted way to keep the GPU hot during self-play. StackExchange answers and academic papers explicitly say “run multiple games to achieve batching,” and Cazenave’s “Batch MCTS” formalizes merged ideas (tree stats local; evals batched/TT-cached). ([Artificial Intelligence Stack Exchange][1])

### B) Process vs thread

* Prefer **process-level actors** (Python side) to dodge GIL interaction and get cleaner memory/CPU isolation. Each actor’s heavy work is in C++, but process separation helps scheduling and avoids one process becoming a stop-the-world point. (Your batcher can live in a main process, receiving ZMQ/pipe messages or shared-memory handles.)

### C) Parameter starting point (for 5900X + 3060 Ti)

* **Actors (G):** start at **8–12**.
* **Threads per actor (t):** **1–2** (shared-tree parallelism within a game still works, but small t keeps contention down and lets G grow).
* **Total CPU threads:** ~10–12 + batcher thread fits your 12 cores (avoid oversubscribing into SMT unless profiling says it helps).
* **Batcher:** max batch **64**, timeout **1–2 ms** (tune); set a global cap on in-flight requests (e.g., a few thousand) to prevent runaway memory.
* **Backpressure:** If queue depth > threshold or GPU util > 95%, temporarily **throttle** actors (token-bucket: each actor allowed N outstanding leaves; refill rate ~inferences/sec ÷ G).

### D) Make your caches global

* **NN-eval cache** (policy/value cache, not shared stats) should be **global and shared across actors** keyed by `(hash, net_version, rules)`. This cuts duplicate NN calls across games. (LC0 uses an NN cache; it’s a proven win.) ([Leela Chess Zero][6])
* Keep it sharded with versioned eviction. (This combines perfectly with multi-game batching, and matches Batch-MCTS suggestions to store evals in TT while keeping stats per tree.) ([arXiv][4])

### E) Scheduling & fairness

* **Per-actor budget**: allocate **visits/move** (or time/move) to avoid starvation if some games are more tactically complex.
* **Adaptive #actors**: auto-increase G until **avg batch ≥ 0.8×max** and **GPU util ~85–95%**; decrease G if per-move visits drop below your training floor.

# fastmctsnet_game_agnostic.py
# ------------------------------------------------
# Game-agnostic, fast AlphaZero-style backbone:
# - Entry/Exit: RepVGG-like + ECA (train multi-branch → fuse for deploy)
# - Middle: choose "ghost" (default) or "shuffle" bottlenecks
# - Policy heads: GridPolicy (H×W → H*W) or FlatPolicy (N actions), pluggable
# - Optional: early-exit heads (entropy/|value| gating) that DO NOT change your APIs
#
# Primary IO (unchanged for your MCTS/loss):
#   outputs = model(x, legal_mask=None, inference=False, return_aux=False)
#   -> outputs["policy_logits"]: (B, policy_dim)
#   -> outputs["value"]: (B, 1)
#
# After training, call:
#   model.switch_to_deploy()   # fuse Rep blocks for max inference speed

from dataclasses import dataclass
from typing import Optional, Tuple, List, Literal, Dict

import torch
import torch.nn as nn
import torch.nn.functional as F


# ---------- ECA: efficient channel attention ----------
class ECA(nn.Module):
    def __init__(self, channels: int, k: int = 5):
        super().__init__()
        self.pool = nn.AdaptiveAvgPool2d(1)
        self.conv = nn.Conv1d(1, 1, kernel_size=k, padding=k // 2, bias=False)
        self.sig = nn.Sigmoid()

    def forward(self, x):
        # x: (B,C,H,W)
        y = self.pool(x)                       # (B,C,1,1)
        y = y.squeeze(-1).transpose(1, 2)      # (B,1,C)
        y = self.conv(y)                       # (B,1,C)
        y = self.sig(y).transpose(1, 2).unsqueeze(-1)  # (B,C,1,1)
        return x * y


# ---------- BN folding helpers for Rep blocks ----------
def _fuse_conv_bn_wb(conv: nn.Conv2d, bn: nn.BatchNorm2d):
    w = conv.weight
    b = conv.bias if conv.bias is not None else torch.zeros(w.size(0), device=w.device)
    g, beta, mean, var, eps = bn.weight, bn.bias, bn.running_mean, bn.running_var, bn.eps
    std = torch.sqrt(var + eps)
    w_fused = w * (g / std).reshape(-1, 1, 1, 1)
    b_fused = beta + (b - mean) * (g / std)
    return w_fused, b_fused

def _pad_1x1_to_3x3(w):
    if w is None:
        return None
    out_c, in_c, _, _ = w.shape
    w3 = torch.zeros((out_c, in_c, 3, 3), dtype=w.dtype, device=w.device)
    w3[:, :, 1:2, 1:2] = w
    return w3

def _id_kernel_3x3(out_c: int, in_c: int, device):
    k = torch.zeros((out_c, in_c, 3, 3), device=device)
    if out_c == in_c:
        idx = torch.arange(out_c, device=device)
        k[idx, idx, 1, 1] = 1.0
    return k


# ---------- Rep-ECA block (train→deploy) ----------
class RepECA(nn.Module):
    def __init__(self, in_ch, out_ch, stride=1, use_eca=True):
        super().__init__()
        self.in_ch, self.out_ch, self.stride = in_ch, out_ch, stride
        self.deploy = False

        self.conv3 = nn.Conv2d(in_ch, out_ch, 3, stride=stride, padding=1, bias=False)
        self.bn3 = nn.BatchNorm2d(out_ch)

        self.conv1 = nn.Conv2d(in_ch, out_ch, 1, stride=stride, padding=0, bias=False)
        self.bn1 = nn.BatchNorm2d(out_ch)

        self.has_id = (in_ch == out_ch and stride == 1)
        self.id_bn = nn.BatchNorm2d(out_ch) if self.has_id else None

        self.eca = ECA(out_ch, k=5) if use_eca else nn.Identity()
        self.act = nn.ReLU(inplace=True)
        self.rbr_reparam = None

    @torch.no_grad()
    def get_equivalent_kernel_bias(self):
        k3, b3 = _fuse_conv_bn_wb(self.conv3, self.bn3)
        k1, b1 = _fuse_conv_bn_wb(self.conv1, self.bn1)
        k1 = _pad_1x1_to_3x3(k1)

        if self.has_id:
            kid = _id_kernel_3x3(self.out_ch, self.in_ch, self.conv3.weight.device)
            g, beta = self.id_bn.weight, self.id_bn.bias
            mean, var, eps = self.id_bn.running_mean, self.id_bn.running_var, self.id_bn.eps
            std = torch.sqrt(var + eps)
            kid = kid * (g / std).reshape(-1, 1, 1, 1)
            bid = beta - mean * (g / std)
        else:
            kid = torch.zeros_like(k3)
            bid = torch.zeros_like(b3)

        return k3 + k1 + kid, b3 + b1 + bid

    @torch.no_grad()
    def switch_to_deploy(self):
        if self.deploy:
            return
        k, b = self.get_equivalent_kernel_bias()
        self.rbr_reparam = nn.Conv2d(self.in_ch, self.out_ch, 3, stride=self.stride, padding=1, bias=True)
        self.rbr_reparam.weight.data.copy_(k)
        self.rbr_reparam.bias.data.copy_(b)
        # drop train-time branches
        for m in [self.conv3, self.bn3, self.conv1, self.bn1, self.id_bn]:
            if m is not None:
                m.requires_grad_(False)
        self.conv3 = self.bn3 = self.conv1 = self.bn1 = self.id_bn = None
        self.deploy = True

    def forward(self, x):
        if self.deploy:
            y = self.rbr_reparam(x)
        else:
            y = self.bn3(self.conv3(x)) + self.bn1(self.conv1(x))
            if self.has_id:
                y = y + self.id_bn(x)
        y = self.eca(y)
        return self.act(y)


# ---------- Ghost bottleneck ----------
class GhostModule(nn.Module):
    def __init__(self, in_ch, out_ch, ratio=2, k=1, dwk=3, stride=1, relu=True):
        super().__init__()
        mid = int(round(out_ch / ratio))
        rem = out_ch - mid
        self.primary = nn.Sequential(
            nn.Conv2d(in_ch, mid, k, stride, k // 2 if k > 1 else 0, bias=False),
            nn.BatchNorm2d(mid),
            nn.ReLU(inplace=True) if relu else nn.Identity(),
        )
        self.cheap = nn.Sequential(
            nn.Conv2d(mid, rem, dwk, 1, dwk // 2, groups=mid, bias=False),
            nn.BatchNorm2d(rem),
            nn.ReLU(inplace=True) if relu else nn.Identity(),
        )

    def forward(self, x):
        y = self.primary(x)
        z = self.cheap(y)
        return torch.cat([y, z], dim=1)

class GhostBottleneck(nn.Module):
    def __init__(self, in_ch, hidden_ch, out_ch, stride=1, use_eca=True):
        super().__init__()
        self.conv1 = GhostModule(in_ch, hidden_ch, relu=True)
        self.dw = nn.Conv2d(hidden_ch, hidden_ch, 3, stride=stride, padding=1, groups=hidden_ch, bias=False)
        self.dw_bn = nn.BatchNorm2d(hidden_ch)
        self.conv2 = GhostModule(hidden_ch, out_ch, relu=False)
        self.eca = ECA(out_ch, k=3) if use_eca else nn.Identity()
        self.short = nn.Identity() if (stride == 1 and in_ch == out_ch) else nn.Sequential(
            nn.Conv2d(in_ch, out_ch, 1, stride=stride, bias=False),
            nn.BatchNorm2d(out_ch),
        )
        self.act = nn.ReLU(inplace=True)

    def forward(self, x):
        out = self.conv1(x)
        out = self.dw_bn(self.dw(out))
        out = self.conv2(out)
        out = self.eca(out)
        out = out + self.short(x)
        return self.act(out)


# ---------- ShuffleNetV2 unit ----------
def channel_shuffle(x, groups=2):
    b, c, h, w = x.size()
    assert c % groups == 0
    x = x.reshape(b, groups, c // groups, h, w).transpose(1, 2).contiguous()
    return x.reshape(b, c, h, w)

class ShuffleV2Unit(nn.Module):
    def __init__(self, channels, use_eca=True):
        super().__init__()
        half = channels // 2
        self.branch = nn.Sequential(
            nn.Conv2d(half, half, 1, 1, 0, bias=False),
            nn.BatchNorm2d(half),
            nn.ReLU(inplace=True),
            nn.Conv2d(half, half, 3, 1, 1, groups=half, bias=False),
            nn.BatchNorm2d(half),
            nn.Conv2d(half, half, 1, 1, 0, bias=False),
            nn.BatchNorm2d(half),
            nn.ReLU(inplace=True),
        )
        self.eca = ECA(channels, k=3) if use_eca else nn.Identity()

    def forward(self, x):
        x1, x2 = torch.chunk(x, 2, dim=1)
        y2 = self.branch(x2)
        y = torch.cat([x1, y2], dim=1)
        y = channel_shuffle(y, 2)
        return self.eca(y)


# ---------- Policy heads (game-agnostic) ----------
class GridPolicyHead(nn.Module):
    """For board games with fixed H×W action space. Returns (B, H*W)."""
    def __init__(self, in_ch: int):
        super().__init__()
        self.head = nn.Sequential(
            nn.Conv2d(in_ch, 2, 1, bias=False), nn.BatchNorm2d(2), nn.ReLU(inplace=True),
            nn.Conv2d(2, 1, 1, bias=True)
        )
    def forward(self, x):  # (B,C,H,W) -> (B, H*W)
        y = self.head(x)  # (B,1,H,W)
        B, _, H, W = y.shape
        return y.view(B, H * W)

class FlatPolicyHead(nn.Module):
    """For arbitrary fixed-dim action encodings (e.g., chess move list). Returns (B, N)."""
    def __init__(self, in_ch: int, action_dim: int):
        super().__init__()
        self.pool = nn.AdaptiveAvgPool2d(1)
        self.fc = nn.Sequential(
            nn.Conv2d(in_ch, 64, 1, bias=False), nn.BatchNorm2d(64), nn.ReLU(inplace=True),
            nn.Conv2d(64, action_dim, 1, bias=True)
        )
    def forward(self, x):  # (B,C,H,W) -> (B,N)
        y = self.fc(self.pool(x))  # (B,N,1,1)
        return y.squeeze(-1).squeeze(-1)

class ValueHead(nn.Module):
    def __init__(self, in_ch: int, hidden: int = 128):
        super().__init__()
        self.conv = nn.Sequential(
            nn.Conv2d(in_ch, 1, 1, bias=False), nn.BatchNorm2d(1), nn.ReLU(inplace=True)
        )
        self.fc = nn.Sequential(
            nn.Linear(1, hidden), nn.ReLU(inplace=True), nn.Linear(hidden, 1), nn.Tanh()
        )
    def forward(self, x):
        y = self.conv(x)
        y = F.adaptive_avg_pool2d(y, 1).view(y.size(0), -1)
        return self.fc(y)  # (B,1)


# ---------- Early-exit head (optional) ----------
class EarlyExitHead(nn.Module):
    def __init__(self, in_ch: int, head_kind: Literal["grid", "flat"], action_dim: Optional[int]):
        super().__init__()
        self.kind, self.action_dim = head_kind, action_dim
        self.policy = GridPolicyHead(in_ch) if head_kind == "grid" else FlatPolicyHead(in_ch, action_dim)
        self.value = ValueHead(in_ch)
    def forward(self, x):
        return self.policy(x), self.value(x)

# ---------- Backbone ----------
class FastBackbone(nn.Module):
    def __init__(self, cfg: ModelConfig):
        super().__init__()
        C, self.cfg = cfg.trunk_channels, cfg
        self.stem = nn.Sequential(nn.Conv2d(cfg.in_planes, C, 3, 1, 1, bias=False),
                                  nn.BatchNorm2d(C), nn.ReLU(inplace=True))
        blocks = []
        # entry Rep-ECA
        for _ in range(cfg.blocks[0]):
            blocks.append(RepECA(C, C, use_eca=cfg.use_eca))
        # middle
        for _ in range(cfg.blocks[1]):
            if cfg.middle_kind == "ghost":
                blocks.append(GhostBottleneck(C, hidden_ch=C, out_ch=C, stride=1, use_eca=cfg.use_eca))
            else:
                if C % 2: raise ValueError("ShuffleV2 requires even channels.")
                blocks.append(ShuffleV2Unit(C, use_eca=cfg.use_eca))
        # exit Rep-ECA
        for _ in range(cfg.blocks[2]):
            blocks.append(RepECA(C, C, use_eca=cfg.use_eca))
        self.blocks = nn.ModuleList(blocks)

    def switch_to_deploy(self):
        for m in self.blocks:
            if isinstance(m, RepECA):
                m.switch_to_deploy()

    def forward_feature(self, x, collect_intermediates: bool = False):
        feats = []
        x = self.stem(x)
        idx = 0
        for m in self.blocks:
            x = m(x); idx += 1
            if collect_intermediates:
                feats.append((idx, x))
        return x, feats

class FastMCTSNet(nn.Module):
    def __init__(self, cfg: ModelConfig):
        super().__init__()
        self.cfg = cfg
        self.backbone = FastBackbone(cfg)

        # policy head
        if cfg.policy_kind == "grid":
            assert cfg.board_size is not None, "board_size=(H,W) required for grid policy"
            self.policy_head = GridPolicyHead(cfg.trunk_channels)
            self.policy_dim = cfg.board_size[0] * cfg.board_size[1]
        else:
            assert cfg.action_dim is not None, "action_dim required for flat policy"
            self.policy_head = FlatPolicyHead(cfg.trunk_channels, cfg.action_dim)
            self.policy_dim = cfg.action_dim

        self.value_head = ValueHead(cfg.trunk_channels)

        # early-exit heads (optional)
        self.ee_points = cfg.early_exit_at or []
        self.ee_heads = None
        if len(self.ee_points) > 0:
            self.ee_heads = nn.ModuleDict({
                str(i): EarlyExitHead(cfg.trunk_channels, cfg.policy_kind, cfg.action_dim)
                for i in self.ee_points
            })

    @torch.no_grad()
    def switch_to_deploy(self):
        self.backbone.switch_to_deploy()

    @staticmethod
    def _entropy_from_logits(logits: torch.Tensor, legal_mask: Optional[torch.Tensor]):
        if legal_mask is not None:
            logits = logits.masked_fill(~legal_mask.bool(), float("-inf"))
        logp = F.log_softmax(logits, dim=-1)
        p = logp.exp()
        return -(p * logp).sum(dim=-1)  # (B,)

    def forward(self, x, legal_mask: Optional[torch.Tensor] = None,
                inference: bool = False, return_aux: bool = False) -> Dict[str, torch.Tensor]:
        cfg = self.cfg
        outputs: Dict[str, torch.Tensor] = {}

        use_ee = inference and self.ee_heads is not None and (cfg.exit_entropy_thr or cfg.exit_value_thr)
        if use_ee:
            feat, feats = self.backbone.forward_feature(x, collect_intermediates=True)
            chosen = None
            for (idx, f) in feats:
                if str(idx) in self.ee_heads:
                    p_logits, v = self.ee_heads[str(idx)](f)
                    ent = self._entropy_from_logits(p_logits, legal_mask)
                    v_abs = v.abs().squeeze(-1)
                    ok = torch.ones(p_logits.size(0), dtype=torch.bool, device=p_logits.device)
                    if cfg.exit_entropy_thr is not None:
                        ok = ok & (ent <= cfg.exit_entropy_thr)
                    if cfg.exit_value_thr is not None:
                        ok = ok | (v_abs >= cfg.exit_value_thr)
                    if bool(ok.all().item()):
                        outputs["policy_logits"] = p_logits
                        outputs["value"] = v
                        chosen = idx
                        break
            if chosen is None:
                outputs["policy_logits"] = self.policy_head(feat)
                outputs["value"] = self.value_head(feat)
            if return_aux:
                outputs["ee_chosen_at"] = torch.tensor([-1 if chosen is None else chosen], device=x.device)
            return outputs

        # standard path
        feat, _ = self.backbone.forward_feature(x, collect_intermediates=False)
        outputs["policy_logits"] = self.policy_head(feat)
        outputs["value"] = self.value_head(feat)
        return outputs

Below are **architecture-level changes** that beat “just shrink the ResNet,” keep **superhuman** play in Gomoku/Renju/Omok, and run *noticeably faster* on your 3060 Ti. Each item includes why it helps, what to change, estimated speed/quality trade-off, and concrete wiring tips.

# 1) ResNet → **Re-parameterizable ResNet (RepVGG / DBB style) + ECA**

**Idea.** Train with multi-branch residuals (3×3 + 1×1 + identity), then **fuse to a single 3×3 conv** per block at inference. Replace SE with **ECA** (Efficient Channel Attention: a tiny 1-D conv over channel stats).

* **Why it helps**: you keep representational power during training, yet inference becomes **one conv + BN** per block (no SE MLPs, no extra branches). ECA gives SE-like gains at **near-zero** overhead.
* **Swap-in**:

  * Training block: Conv3×3 + Conv1×1 (+ identity), BN each, **ECA** after the sum.
  * Export: fuse (Conv+BN) branches → **one** Conv3×3+BN; drop ECA to a cheap 1-D conv (k=3/5).
* **Throughput gain**: **+25–50%** vs your current ResNet+SE at the **same depth/width** (typical), minimal strength loss; often strength holds or improves due to richer training graph.
* **Notes**: Keep kernel count modest (C=48–64). For Gomoku, 10–12 fused blocks is a sweet spot.

---

# 2) **Ghost bottleneck residuals** (+ECA), not depthwise-only MobileNet

**Idea.** Replace some heavy convs with **Ghost modules** (generate many feature maps via cheap linear ops from a few “intrinsic” maps). Wrap in a residual bottleneck and keep ECA.

* **Why it helps**: large **FLOP drop** without starving channels; better than straight depthwise on 15×15 where memory traffic dominates.
* **Swap-in**: Residual( Ghost(1×1) → Ghost(3×3) ) with **stride 1**, ECA on the shortcut sum.
* **Throughput gain**: **+30–70%** vs plain ResNet at same C,B; small risk of slight tactical sensitivity loss—mitigate with data aug + auxiliary losses (below).

---

# 3) **ShuffleNetV2-style bottlenecks** (channel split + shuffle) **only for middle blocks**

**Idea.** Use **channel-split** bottlenecks (half pass identity, half go through 1×1→3×3→1×1) and **shuffle** channels to mix information cheaply.

* **Why it helps**: reduces **memory bandwidth pressure** and MACs in the trunk mid-depth where features are widest.
* **Where**: Keep **first 2–3 blocks** and **last 2 blocks** as normal (policy/value prefer clean features). Use ShuffleV2 units in the **middle 4–8 blocks**.
* **Throughput gain**: **+15–35%** on top of #1 or #2, with minimal impact when confined to the middle.

---

# 4) **Two-tier evaluator cascade** (tiny gate → main net), integrated with MCTS

**Idea.** Run a **micro-net** first (C=24–32, B=2–3; ~0.05–0.12 M params). If its **policy entropy is low** or it flags clear tactical motifs (immediate five/open four), **accept** its output; else **escalate** to the main net.

* **Why it helps**: many Gomoku nodes are trivial (forceds, dead shapes). You avoid calling the main net **30–60%** of the time.
* **Gate**: `if H(policy) < τ or threat_flag==True → accept; else escalate`
* **Throughput gain (end-to-end)**: **×1.5–×2.5** typical depending on τ and tree shape.
* **Strength**: Preserve superhuman: set τ via validation so the gate is conservative in ambiguous positions; let MCTS visit count absorb the small noise from the micro-net.

---

# 5) **Early-exit heads** (block-3 / block-6) with confidence gating

**Idea.** Add **auxiliary policy/value heads** at earlier depths. If the head’s **value confidence** (|v|) or **policy entropy** is decisive, **stop forward** and return. Otherwise continue full forward.

* **Why it helps**: saves compute **when positions are obvious**; no change to the main net capacity.
* **Throughput gain**: **×1.2–×1.6** average (stackable with #4). Calibrate per-game (Gomoku lets more early exits than chess).
* **Tip**: During training, attach deep supervision (small λ on aux losses). At inference, freeze confidence thresholds to hit your target sims/sec.

---

# 6) **Auxiliary tactical heads** (cheap) to protect strength with lighter trunks

**Idea.** Add auxiliary classifiers (multi-label) that predict:

* **immediate five / open four / open three** (per player)
* **run-length-to-five maps** (discretized bins)

Back-propagate these with small weights.

* **Why it helps**: small nets learn **threat semantics** faster & retain them after replacing SE/standard residuals.
* **Overhead**: negligible; heads are 1×1 conv + tiny loss.
* **Effect**: recovers much of “tactical bite” lost by Ghost/Shuffle substitutions; boosts the **gate** (#4) reliability.

---

# 7) **Lightweight attention alternatives** to SE

If you really like channel attention but want it cheaper:

* **ECA** (recommended default): 1-D conv on global-avg pooled channels.
* **Coord-Attention** (CA): embeds positional info with split-axis pooling; use **small reduction** to keep FLOPs down.
* **CBAM-lite**: channel only, drop spatial branch.

**Throughput gain vs SE**: **+5–10%** typically (module overhead ↓), with similar or better strength than SE in Gomoku.
